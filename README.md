`pgsentinel` – sampling active session history
=============================================================

[![Build Status](https://github.com/pgsentinel/pgsentinel/actions/workflows/regression.yml/badge.svg)](https://github.com/pgsentinel/pgsentinel/actions/workflows/regression.yml)

This build: `pgsentinel_nx`
---------------------------

This repository builds pgsentinel as `pgsentinel_nx`, so that it can be
installed and loaded in the same PostgreSQL server as vanilla `pgsentinel`.
Everything two copies would otherwise share carries the `_nx` suffix:

| | vanilla | this build |
|---|---|---|
| extension (`CREATE EXTENSION`) | `pgsentinel` | `pgsentinel_nx` |
| library (`shared_preload_libraries`) | `pgsentinel` | `pgsentinel_nx` |
| parameters | `pgsentinel.db_name`, `pgsentinel_ash.*`, `pgsentinel_pgssh.*` | `pgsentinel_nx.db_name`, `pgsentinel_nx_ash.*`, `pgsentinel_nx_pgssh.*` |
| background worker | `pgsentinel` | `pgsentinel_nx` |
| shared memory and global C symbols | | names of their own |

The views and functions keep their names (`pg_active_session_history`,
`pg_stat_statements_history`, `get_parsedinfo()`), so queries written for
vanilla pgsentinel work unchanged. The two extensions therefore can't share a
schema. To run both, install them in different schemas or databases, and
point each worker at the database that holds its extension:

    shared_preload_libraries = 'pg_stat_statements,pgsentinel,pgsentinel_nx'
    pgsentinel.db_name = 'postgres'
    pgsentinel_nx.db_name = 'postgres'

    CREATE SCHEMA nx;
    CREATE EXTENSION pgsentinel;
    CREATE EXTENSION pgsentinel_nx SCHEMA nx;

    SELECT * FROM nx.pg_active_session_history;

Switching a database from vanilla pgsentinel to this build is a new
installation, not an upgrade: `DROP EXTENSION pgsentinel`, then
`CREATE EXTENSION pgsentinel_nx`. The history is kept in memory, so only
objects you built on top of the views need recreating.

The rest of this document describes pgsentinel in general, with the commands
and parameter names of this build.

Introduction
------------

PostgreSQL provides session activity. However, in order to gather activity
behavior, users have to sample the pg_stat_activity view multiple times.
`pgsentinel` is an extension to record active session history and link
 the activity with query statistics (`pg_stat_statements`).

The module must be loaded by adding `pgsentinel_nx` to
`shared_preload_libraries` in postgresql.conf, which means a server restart
is needed.

When `pgsentinel` is enabled, it collects the history of session activity:

 * It's implemented as an in-memory ring buffer where
   samples are written with a given (configurable)
   period.  Therefore, the user can see some number of
   recent samples depending on the history size (configurable).

In combination with `pg_stat_statements`, this extension can link the session activity with
query statistics.

To get more granular queries statistics, `pgsentinel` samples the `pg_stat_statements` view:

 * at the same time it is sampling the active sessions
 * only for the queryid associated to an active session (if any) during the sampling

`pgsentinel` launches a special background worker for gathering session activities.

Availability
------------

`pgsentinel` is implemented as an extension and not available in the default
PostgreSQL installation. It is available from
[github](https://github.com/pgsentinel/pgsentinel)
under the same license as
[PostgreSQL License](https://github.com/pgsentinel/pgsentinel/blob/master/LICENSE)
and supports PostgreSQL 9.6+.

Installation
------------

`pgsentinel` is a PostgreSQL extension which requires PostgreSQL 9.6 or
higher. Before the build and install steps, you should ensure the following:

 * PostgreSQL version is 9.6 or higher.
 * You have the development package of PostgreSQL installed or you built
   PostgreSQL from source.
 * Your `PATH` variable configuration includes `pg_config`, or
   you've set a value for `PG_CONFIG`.

The typical installation procedure may look like:

As `pgsentinel` uses the `pg_stat_statements` extension (officially bundled with PostgreSQL) for tracking which queries get executed in your database, add the following entries to your postgres.conf:

    $ shared_preload_libraries = 'pg_stat_statements,pgsentinel_nx'
    $ # Increase the max size of the query strings Postgres records
    $ track_activity_query_size = 2048
    $ # Track statements generated by stored procedures as well
    $ pg_stat_statements.track = all

restart the postgresql daemon and create the extension:

    $ git clone https://github.com/andrewdmit/pgsentinel.git
    $ cd pgsentinel/src
    $ make
    $ sudo make install
    $ psql DB -c "CREATE EXTENSION pgsentinel_nx;"


Testing
-------

The regression tests start throwaway PostgreSQL instances, so they need the
server binaries (`initdb`, `postgres`) of the version `pg_config` points at and
must run as a non-root user. After `make install`:

    $ cd pgsentinel/src
    $ make installcheck-all

Each suite gets a fresh instance, and no running server is touched. `make`
exits non-zero if anything fails, so the command can run unattended:

 * `pgsentinel-test`: sampling, `queryid` and `nested_queryid`, idle in
   transaction tracking, `pg_stat_statements_history`, privileges;
 * `pgsentinel-upgrade-test`: the library serves the 1.4.1 and 1.5.1 SQL
   definitions of the view until `ALTER EXTENSION pgsentinel_nx UPDATE`, and
   objects built on the view survive the update;
 * `pgsentinel-blockers` (isolation test): `blockers`, `blockerpid` and
   `blocker_state` checked against `pg_blocking_pids()` for a row lock wait,
   for a table lock held by two sessions, and for a parallel query whose worker
   waits on a lock, along with the waiter's other columns;
 * `pgsentinel-disabled-test`: sampling with `pgsentinel_nx_pgssh.enable = off`.

A failure leaves its differences in `regression.diffs` and
`output_iso/regression.diffs`.

`DEB_BUILD_GNU_TYPE=1 make installcheck` runs the suites against a server that
is already running instead, which is how CI uses them. That server has to be
newly created with `pgsentinel.conf` appended to its configuration: the tests
expect an empty session history and a `contrib_regression` database that
pgsentinel's worker is not yet attached to, and they leave
`pgsentinel_nx_ash.track_idle_trans` on through `ALTER SYSTEM`. Don't point them
at a server you care about.

You can see it as samplings of `pg_stat_activity` providing more information:

* `ash_time`: the sampling time
* `top_level_query`: the top-level statement from `pg_stat_activity.query` (in case PL/pgSQL is used)
* `query`: the statement currently being executed, from `get_parsedinfo()` (not normalised, so parameter values are visible)
* `cmdtype`: the statement type (SELECT,UPDATE,INSERT,DELETE,UTILITY,UNKNOWN,NOTHING)
* `queryid`: the top-level query ID from `pg_stat_activity.query_id`[^1], which links to `pg_stat_statements`
* `nested_queryid`: the query ID returned by `get_parsedinfo()` for the statement currently being executed
* `blockers`: the number of blockers
* `blockerpid`: the pid of the blocker (if blockers = 1), the pid of one blocker (if blockers > 1)
* `blocker_state`: state of the blocker (state of the blockerpid) 

### Sampler implementation

On every tick `pgsentinel` collects ASH samples by calling the built-in
functions `pg_stat_get_activity()` and `pg_blocking_pids()` directly through
the fmgr, rather than by executing a large `pg_stat_activity` self-join through
SPI. This avoids the cost of parsing, planning and executing that query on each
sample while still relying only on PostgreSQL's own documented functions: the
extension consumes the rows `pg_stat_get_activity()` returns and the array of
blocking pids `pg_blocking_pids()` returns, and builds the blocker resolution
around those results instead of duplicating any core algorithm inside the
extension. `pg_blocking_pids()` reports on a session's whole lock group (a
parallel leader and its workers) and finds nothing unless some member waits on
a heavyweight lock, so it is called only for the sessions of such groups.

Switching to the direct calls did not change the columns of
`pg_active_session_history` or the extension's configuration. One value
behaves differently: with `compute_query_id = off`,
`pg_stat_activity.query_id` is empty, and `queryid` now falls back to the id
`pgsentinel` computes in its own parse hook instead of being reported as `0`.
With `compute_query_id = on` — the setting that makes `queryid` joinable to
`pg_stat_statements` — the value is unchanged.

#### Sampling overhead

Cost of one sample, measured on PostgreSQL 16.15 with 4 vCPUs. Vanilla
pgsentinel 1.5.2 and this build ran in the same server at the same time, so
both described the same sessions, with `pg_stat_statements_history` off for
both. Sessions were held `active` with `pg_sleep()`; the figures are each
worker's own CPU time from `/proc/<pid>/schedstat` over 60 seconds, divided by
the samples it took, and every sample of both recorded all the sessions.

| Active sessions | SPI/SQL sampler | Direct calls | Ratio |
|---:|---:|---:|---:|
| 25  | 2.23 ms  | 0.32 ms | 7x  |
| 50  | 3.58 ms  | 0.38 ms | 9x  |
| 100 | 7.49 ms  | 0.50 ms | 15x |
| 200 | 21.77 ms | 0.60 ms | 36x |

The ratio widens with concurrency because the two samplers scale differently:
going from 100 to 200 sessions multiplies the SQL sampler's cost by 2.9 (it
self-joins `pg_stat_activity` and calls `pg_blocking_pids()` twice per row),
and the direct path's by 1.2, as most of what it still spends is per sample
rather than per session.

Two further choices keep the direct path's cost down. Each cycle the worker
looks up its schema with a catalog query; it keeps the plan of that query
rather than parsing and planning it again, and runs it only when
`pg_stat_statements_history` needs the schema. And it skips
`pg_blocking_pids()` for sessions that can't be blocked. Each call takes
`ProcArrayLock` and all 16 lock manager partition locks, which other backends
need to acquire and release heavyweight locks, so asking only where an answer
is possible also stays out of the workload's way.

In absolute terms the sampler is cheap either way at the default one second
period: 21.77 ms per second is about 2% of a single core. The difference
matters on instances with many active sessions, on machines that are already
CPU bound, or where the periodic planner work of the old statement was itself
the problem.

[^1]: When `pg_stat_activity.query_id` is not available — before PostgreSQL 14, or with `compute_query_id = off` — `queryid` falls back to the id from `get_parsedinfo()` and therefore matches `nested_queryid`.

Remark
-------------------------

* Some fields may be NULL depending on the version (for example, `leader_pid` is NULL for version <= 13.0...)
* Since 1.5.1, `PUBLIC` can't execute `get_parsedinfo()`, which returns the raw query text of every backend. An existing install gets this only after `ALTER EXTENSION pgsentinel_nx UPDATE`, run in each database that has the extension. A role granted `EXECUTE` sees the query text of all sessions.
